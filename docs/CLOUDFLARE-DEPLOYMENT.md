# نشر OUD على Cloudflare Workers

هذه النسخة تعمل عبر Next.js/OpenNext + PostgreSQL في Supabase. لا تُرفع صورة Docker إلى Workers، ولا يتصل المتصفح بجداول Supabase مباشرة. لا تحتاج واجهة النظام إلى مفاتيح Supabase العامة أو السرية.

## قبل ربط GitHub

1. استخدم نسخة مصدر نظيفة من دون `.git` القديمة أو `.env` أو النسخ الاحتياطية أو التقارير أو ملف Excel الحقيقي. سكربت `npm run release:source` يجهّز نسخة قابلة للرفع. لا ترفع تاريخ المستودع المحلي القديم الذي سبق أن تتبع ملف البيئة.
2. دوّر كلمة مرور قاعدة البيانات ومفتاح Supabase السري اللذين سبق تداولهما قبل النشر العام. لا تدخل القيم إلى الكود أو إعدادات `NEXT_PUBLIC_*`.
3. أنشئ staging منفصلة عن قاعدة العمل أولًا، وحدد الدومين والمنطقة الحقيقية للقاعدة والخطة. حدود Workers المستخدمة هنا تتطلب خطة تدعم CPU المهيأ والـQueues وR2؛ لا تعتبر نجاح البناء إثباتًا لحدود حسابك.
4. احتفظ بنسخة PostgreSQL قابلة للاستعادة قبل الترحيل. الأدوات المجدولة الموجودة في `scripts/backup*.mjs` تعمل في runner مناسب به `pg_dump` وrestic، لا داخل Workers. ملفات R2 المؤقتة ليست بديلًا للنسخ الخارجي المجدول.

## المخطط وحساب التشغيل

- استخدم اتصال المالك الخاص للترحيلات فقط: `npm ci` ثم `npm run db:migrate`. نفّذها في runner خاص مع `DATABASE_URL` من مخزن الأسرار، وليس أثناء أول طلب من مستخدم.
- الترحيلان الإضافيان `202610290001_data_protocol` و`202610290002_background_jobs` يضيفان الإيصالات والإصدارات والمهام. لا يحذفان العمليات المالية أو يعيدان تهيئة الأرصدة.
- راجع ونفذ `prisma/operations/runtime-role.sql` بحساب المالك؛ عيّن كلمة مرور جديدة وLOGIN للدور `oud_runtime` بصورة خاصة. لا توجد كلمة مرور داخل الملف. الدور يقرأ ويعدل جداول التطبيق فقط، ولا يحصل على DDL أو ملكية الجداول أو دور Supabase API.
- طبّق ملف منح الصلاحيات بعد أي ترحيل يضيف جدولًا جديدًا. يستخدم Hyperdrive حساب `oud_runtime`، وتبقى بيانات المالك خارج Worker.
- إعداد RLS في هذا الملف يسمح لدور الخادم بالعمل، مع حجب الأدوار العامة؛ صلاحيات الموظفين تُطبّق في API. لا تعطِ بيانات هذا الدور للمتصفح.

## موارد Cloudflare

أنشئ الموارد في حسابك، ثم عدّل الأسماء عند الحاجة في `wrangler.jsonc`:

```sh
npx wrangler queues create oud-jobs
npx wrangler r2 bucket create oud-private-jobs
npx wrangler secret put SESSION_SECRET
```

أنشئ Hyperdrive من لوحة Cloudflare باتصال Supabase PostgreSQL الخاص بحساب التشغيل. **عطّل Query Caching**؛ نحتاج تجميع الاتصالات مع قراءة حديثة للصلاحيات والأرصدة. أدخل ID الحقيقي بدل الأصفار في `wrangler.jsonc`، واضبط `vars.APP_URL` على أصل HTTPS النهائي، مثل `https://erp.example.com` دون مسار أو شرطة نهائية.

لا تجعل حاوية R2 عامة. المفاتيح تحفظ ملفات المهام تحت `jobs/`. أضف قاعدة حذف بعد يومين كحد احتفاظ احتياطي إلى جانب التنظيف البرمجي بعد 24 ساعة؛ لا تستخدم هذه الحاوية لنسخ الاحتفاظ الدائم. التنزيل يمر بجلسة مدير وصلاحية ملكية المهمة ولا يستعمل رابطًا عامًا.

[تعطيل كاش Hyperdrive](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/)، [موارد Wrangler](https://developers.cloudflare.com/workers/wrangler/configuration/)، [Prisma مع OpenNext](https://opennext.js.org/cloudflare/howtos/db).

## الربط بالمستودع

- ربط المستودع بـ **Workers Builds**، وليس نشرًا ثابتًا في Pages.
- Node.js 22؛ أمر النشر: `npm run cf:deploy`. هذا الأمر يتحقق من الإعدادات ثم يبني الحزمة وينشرها. إن كان النظام يطلب Build command منفصلًا، استخدم `npm run cf:build` وDeploy command: `node scripts/check-cloudflare-config.mjs && npx wrangler deploy`.
- يجب أن ينجح فحص GitHub `checks` على الفرع المرشح قبل ترقية نسخة الإنتاج. تفعيل النشر التلقائي للإنتاج دون انتظار الفحص يلغي هذا الضمان؛ استخدم فرع staging أولًا أو قواعد دمج تحمي الفرع المنشور.
- لا تحتاج مرحلة البناء إلى اتصال بقاعدة العمل. سكربت البناء يستخدم قيماً وهمية، ويزيل ملفات `.env` التي ينسخها Next.js إلى الحزمة، ويفحص عدم تسرب الأسرار المحلية المعروفة.
- لا تغيّر Hyperdrive ID أو APP_URL عبر أسرار بناء تختلف عن ملف Wrangler دون تحديث الملف المعتمد؛ الإعدادات الناقصة تمنع النشر بدل إنتاج نسخة معطلة.

## الفحص قبل الإطلاق

```sh
npm ci
npm run db:generate
npm run typecheck
npm run lint
npm run cf:build
npm run cf:dry-run
OUD_WORKER_SMOKE=1 npm run test:integration
```

الاختبار الأخير ينشئ قاعدة `oud_test_*` مؤقتة في Docker، ويطبق الترحيلات، ويفحص معاملات النظام، ثم يشغل workerd محليًا للدخول والتقارير والحفظ المتزامن والإيصالات وتعارض التعديل والمهام والتنزيل. لا يقرأ `.env` بوصفه هدف اختبار. قد يُحتاج إلى صلاحية Docker في جهاز التطوير.

قبل الإنتاج افحص نفس العمليات على staging السحابية مع Hyperdrive الحقيقي ومن متصفح الموقع المستهدف. قارن الأرصدة والمخزون والديون قبل الترحيل وبعده، وسجّل p50/p95 للقراءة والحفظ. المحاكاة المحلية لا تقيس RTT أو أداء خطة Cloudflare أو إتاحة IPv6 الفعلية.

## التشغيل والرجوع

- الردود المصادق عليها وAPI تحمل `private, no-store` ولا تُخزن في CDN. كاش المتصفح معزول عن كاش HTTP؛ تفاصيله في `BROWSER-SESSION-CACHE.md`.
- الحفظ المالي يُعتمد في PostgreSQL داخل معاملة. عند تعذر وصول الرد يعيد العميل استخدام مفتاح العملية نفسه؛ لا يعرض نجاحًا ماليًا متفائلًا.
- التعديل يستخدم إصدار السجل الذي شاهده المحرر. يعيد API `428` عند غيابه و`409` عند التعارض. أي تكامل خارجي قديم يعدّل البيانات الأساسية يجب تحديثه لإرسال `If-Match: "<version>"`.
- إبطال كاش الأجهزة الأخرى يتم بفحص revision كل 30 ثانية عندما تكون الصفحة ظاهرة، وبالأحداث بين تبويبات المتصفح. ليس بثًا لحظيًا مضمونًا عبر جميع الأجهزة.
- الاستيراد والاستعادة والتصدير في Workers تنفذ كمهام معاد تسليمها بأمان؛ تغييرات المال ونجاح المهمة في معاملة واحدة. تقارن عملية تطبيق Excel إصدار القاعدة بلحظة المعاينة. حد الملف 10MB للاستيراد و32MB للنسخ؛ النسخ الأكبر تُدار بأدوات PostgreSQL الخارجية.
- المهام تعرض الحالة في شاشة النسخ الاحتياطي، وتنتهي صلاحية تنزيل الملفات بعد 24 ساعة. عند فقد الاتصال أعد نفس الطلب أو راجع المهمة؛ لا تنشئ عملية بديلة قبل معرفة نتيجتها.
- راقب أخطاء Worker والمهام وزمن API (`Server-Timing`) ومعرف الطلب (`X-Request-Id`). لا تسجل أجسام الفواتير أو كلمات المرور أو الجلسات.
- الرجوع: أعد نشر إصدار الكود السابق المتوافق مع المخطط. لا تسترجع قاعدة قديمة بعد دخول عمليات مالية جديدة. الترحيلات إضافية؛ احتفظ بها عند الرجوع إلى كود أقدم.

لم يُنفذ هذا الدليل على حساب Cloudflare أو قاعدة الإنتاج تلقائيًا. الإعداد والنشر السحابيان منفصلان عن تسليم الكود.
