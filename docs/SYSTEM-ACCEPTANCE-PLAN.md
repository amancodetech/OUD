# خطة قبول نظام OUD والتحقق من صحة نتائجه

تاريخ الإعداد: 27 أكتوبر 2026. الحالة: **دورة المتابعة:40حالة ناجحة، صفر فاشلة، و4محجوبة**. تفاصيل المتابعة في[تقرير28أكتوبر](../reports/acceptance-remediation-2026-10-28/README.md) و[سجلها](../reports/acceptance-remediation-2026-10-28/results.csv). أدلة الدورة السابقة في [تقرير التنفيذ](../reports/acceptance-2026-10-27/README.md) و[سجل النتائج](../reports/acceptance-2026-10-27/results.csv). يبقى سجل الحالات أدناه وصفًا للخطة الأصلية، ولا تعني نتيجة التنفيذ اجتياز بوابة القبول الشاملة.

الهدف: إصدار حكم موثق على سلامة الحسابات والبيانات والصلاحيات وتجربة الاستخدام وقابلية الاستعادة، مع تسجيل العيوب المتبقية وحدود الفحص. لا تمثل النتيجة ضمانًا بانعدام كل خطأ محتمل.

## 2. ضوابط بيئة التنفيذ

1. تثبيت نسخة مرشح محددة: معرف Git، وبصمات الملفات المعدلة وغير المتتبعة المؤثرة، و`package-lock.json`، وإصدارات Node وPostgreSQL، والتوقيت. معرف Git وحده غير كافٍ في مساحة العمل الحالية ذات التعديلات غير الملتزم بها.
2. استخدام نسخة مصدر مستقلة لبناء الاختبارات والمتصفح، مع اعتماديات وعميل Prisma مولّدين فيها. لا يُربط `node_modules` ببيئة العمل ولا يُنسخ ملف أسرار العمل إلى بيئة الاختبار.
3. كل تجربة إنشاء/إلغاء/استيراد/استعادة/ضغط أو فشل متعمد تعمل في قاعدة `oud_test_<run>` داخل حاوية مخصصة. يُمرر الاتصال صراحةً ويُفحص `current_database()` من PostgreSQL قبل أي كتابة. يفشل التشغيل عند اختلاف الاسم أو الوجهة.
4. يحدد خادم الاختبار عنوانه ومنفذه وسر الجلسة صراحةً، ويستخدم ملف متصفح مستقلًا. تُستعمل بيانات وحسابات اصطناعية؛ لا توجد حاجة إلى كلمة مرور المدير الحقيقي لتنفيذ حالات الكتابة.
5. مطابقة بيانات العمل تتم بقراءات على لقطة ثابتة أو نسخة مستعادة خاصة. إذا لزم أخذ نسخة من العمل، تُحفظ خارج Git بصلاحيات خاصة ويُتحقق من سلامتها. تعطَّل أي مهام أو اتصالات خارجية داخل النسخة المستعادة.
6. قبل إغلاق التشغيل، تُحذف موارد الاختبار المحددة بمعرف التشغيل فقط. لا تُستخدم قواعد تنظيف عامة حسب الاسم أو رقم الهاتف. يُتحقق من عدم وصول أي مستند تجريبي إلى قاعدة العمل.

فشل العزل يوقف الدورة فورًا. لا تُشغّل سكربتات التهيئة القديمة أو `migrate reset` على قاعدة العمل.

تبدأ C وD بعد نجاح A وB. لا تُنفذ تجارب الأعطال قبل نجاح الاستعادة في F. يمكن جمع مستندات الأرصدة خلال العمل التقني؛ نقصها لا يمنع استكمال الاختبارات الاصطناعية لكنه يمنع اعتماد الأرصدة الفعلية.

تقدير أولي للدورة الكاملة: **3–5 أيام عمل** بعد توافر مستندات المصدر، دون وقت إصلاح العيوب المكتشفة أو انتظار مراجعة مالك البيانات. هذا تقدير تنظيم للعمل وليس نتيجة قياس أو موعدًا مضمونًا.

## 4. سيناريو رقمي مستقل للدورة اليومية

يُنفَّذ في قاعدة اختبار منفصلة ونظيفة. جميع المبالغ وحدات نقدية تجريبية من العملة نفسها. يستخدم السيناريو صنفًا واحدًا بتكلفة ثابتة لتكون النتائج قابلة للحساب يدويًا. لا يُستخرج المتوقع من محركات التطبيق أو من استجابات API.

**التهيئة:** سنة البداية 2026؛ خزينة 1,000؛ بنك 2,000؛ صنف بضاعة افتتاحه 10 وحدات وقيمته 100؛ عميل ومورد بأرصدة صفرية؛ رأس مال شريك 3,100؛ لا أصول أو قروض أو أرباح مرحلة أو حركات أخرى. فرق الافتتاح المتوقع صفر. الفترة مفتوحة، ومنع المخزون السالب مفعّل، والافتتاح معلّم كمراجع، ولا أصول افتتاحية معتمدة. لا خصومات أو تكاليف إضافية في هذا السيناريو.

يُنفَّذ السيناريو عبر HTTP الحقيقي ثم عبر المتصفح في قاعدة جديدة لكل تشغيل. تُختبر أيضًا عينات بكميات كسرية وخصومات وتكلفة وصول في حالات مستقلة ذات توقعات محسوبة مسبقًا. لا يُعد نجاح أرقام هذا المثال وحده إثباتًا لكل قواعد التكلفة.

السيناريوهات الذهبية المرجعية الإضافية موصوفة في [specs/16-testing-golden-scenario.md](../specs/16-testing-golden-scenario.md). عند التنفيذ تُراجع الأرقام مقابل ملف التدريب الأصلي وملف Excel المعتمد؛ لم يُتحقق من محتوى ملفيهما مجددًا أثناء إعداد هذه الخطة.

## 5. مراجعة فرق الافتتاح الفعلي

1. استخراج لقطة لكل مكوّن: الخزينة، البنك، مخزون الافتتاح، أرصدة العملاء والموردين والممولين، الأصول المعتمدة وحالة اعتمادها، القروض، رؤوس أموال الشركاء والأرباح المرحلة.
2. إعداد جدول لكل مكوّن يحتوي قيمة النظام، قيمة المستند، تاريخ المصدر، الفرق، والتفسير. يلزم مصدر مستقل: كشف/جرد/إقرار رصيد أو ملف تأسيس معتمد، بحسب المكوّن.
3. إعادة حساب المعادلة المطبقة حاليًا بصورة مستقلة، ثم مراجعة مطابقة مكوناتها وتعريفاتها للمصدر. المعادلة البرمجية هي: النقد والبنك + مخزون الافتتاح + رصيد العملاء + الأصول المعتمدة − رصيد الموردين − القروض − رصيد الممولين − رؤوس أموال الشركاء − الأرباح المرحلة.
4. تصنيف السبب: رقم مصدر مختلف، إشارة أو تصنيف مختلف، تكرار أو نقص، إعداد اعتماد أصل، أو عيب حسابي. لا يُنسب السبب إلى البيانات قبل التحقق.
5. تقديم تصحيح موثق للمراجعة؛ تعديل الأرصدة الفعلية يحتاج مستندًا وموافقة مالك البيانات. لا يوضع مبلغ تسوية عشوائي لمجرد جعل الفرق صفرًا.

**معيار القبول المالي:** تطابق الأرصدة مع مصادرها، وتفسير المعادلة، وإغلاق الفروق غير المبررة. القيمة 178,811,737 ملاحظة قائمة من آخر عرض، وليست رقمًا مستهدفًا أو قيمة يجب فرضها على البيانات.

## 6. تغطية الفحوصات

سجل الحالات التنفيذي في [acceptance-cases.csv](./acceptance-cases.csv). لكل حالة معرف وأولوية وشروط وخطوات ونتيجة متوقعة وتغطية سابقة. جميع حالاته تبدأ بحالة «مخطط» للدورة الجديدة؛ وجود اختبار سابق لا يغيّرها تلقائيًا إلى «ناجح».

- **العمليات:** إنشاء وتعديل البيانات الأساسية، البيع والشراء الآجل والفوري، التسويات المرتبطة بالفواتير، المرتجع الصالح والتالف، الإلغاء، التصنيع، التستر والعينات، السائقون والهدايا، الشركاء والممولون والأصول.
- **الصلاحيات:** جرد كل مسار HTTP وطريقته وإسناد الصلاحية المتوقعة له قبل التشغيل؛ أدوار المدير والمحاسب والكاشير، وحسابات ذات صلاحيات مخصصة مفردة وفارغة. اختبار الحالة المسموحة والحالة الممنوعة لكل صلاحية، بما فيها نوع السند وحقول التكلفة المتداخلة. تُبنى المصفوفة من سياسة التشغيل والمواصفات ومراجعة مالك النظام، لا من قراءة نتيجة الحارس البرمجي وحدها.
- **حدود البيانات:** كميات ومبالغ صفرية وسالبة وغير صالحة، كميات كسرية، تواريخ خاطئة أو سابقة أو مقفلة، أطراف وأصناف غير نشطة، مستندات ملغاة، وتكرار أرقام الفواتير بين السنوات والأطراف حسب قواعد النظام.
- **التزامن:** مولد الأكواد، آخر كمية مخزون، الحفظ المتكرر بمفتاح العملية نفسه، اختلاف الحمولة تحت المفتاح نفسه، واستجابة فقدها العميل بعد إتمام الحفظ.
- **المتصفح:** دورة كاملة بحساب التشغيل، واللغات العربية والإنجليزية والإندونيسية، وعروض 390 و768 و1440px، وفحص 320px للمكونات الحرجة؛ لوحة المفاتيح والتركيز والأخطاء والتحميل؛ طباعة فاتورة A4 والاسم والعملة والأرقام.
- **سلامة النقل:** استيراد ملف صحيح ثم تكراره، ملف غير مطابق، مرجع مفقود، صف معيب وسط ملف، وتغيير الملف بعد المعاينة. يجب ألا يبقى حفظ جزئي بعد الرفض.

للمبالغ ذات التوقعات الصحيحة في المثال أعلاه: التطابق تام. للكميات والقيم الكسرية: تُثبت دقة المقارنة وسياسة التقريب الموثقة لكل حقل قبل الاختبار؛ لا يُقارن نص الشاشة المقرب بحقل قاعدة البيانات كامل الدقة دون مراعاة ذلك، ولا تُوسّع حدود السماح لإخفاء فشل.

## 7. الاستعادة والترحيل والتشغيل

**JSON:** إنشاء نسخة، إضافة حركات لاحقة، ثم استعادتها في قاعدة الاختبار. مقارنة كل جدول مشمول بالمحتوى والمعرفات والعلاقات والقيم، والتأكد من زوال الإضافات اللاحقة. الاستثناءات المتوقعة تُسجّل صراحةً: معرفات الجلسات الجديدة، عداد إصدار الجلسة، سجل RESTORE الجديد، وتصفير بيانات محاولات الدخول التي لا يشملها تصدير JSON. تكرر الاستعادة بالملف نفسه ثم بملف أقدم، ويُتحقق من رفض الجلسات السابقة ومن تراجع المعاملة كاملة عند نسخة معيبة.

**PostgreSQL:** استعادة `pg_dump` إلى قاعدة أخرى فارغة، والتحقق من المحتوى والمخطط والعلاقات والقيود والأرصدة، لا أعداد الصفوف وحدها. إعادة تشغيل التطبيق المستعاد وتسجيل الدخول وقراءة التقارير. عند تحويل نسخة مستعادة إلى تشغيل فعلي، يلزم إجراء إبطال جلسات مناسب وتحديد سرها قبل فتحها للمستخدمين.

**الترحيلات:** المصادر الأربعة التي يفحصها `scripts/verify-migrations.mjs`: المخطط القديم الفعلي، والمخطط الوسيط، والإصدار السابق لمعرف الجلسة، وقاعدة جديدة. المقارنة تشمل بقاء الترجمات والصلاحيات والمبالغ الافتتاحية وتطابق المخطط النهائي؛ الترحيل الثاني لا يضيف تغييرًا آخر.

**النشر:** بناء صورة Docker من المرشح النهائي مع معرف صورة مسجل، وتشغيلها على قاعدة اختبار، والتحقق من الدخول والصلاحيات وCLI الترحيل والأصول والخطوط وتشغيل المستخدم غير الجذر. لا تنقل الصورة أو الترحيل إلى العمل قبل استيفاء بوابة القبول.

**النسخ المجدول:** يُحدد مكان التخزين خارج الجهاز، وتواتر النسخ والاحتفاظ والتنبيه عند الفشل قبل تفعيل المهمة. يُختبر نجاح نسخة مجدولة وفشلها واحتفاظها واستعادتها من الوجهة الفعلية. هدفان أوليان للنقاش قبل التنفيذ: أقصى فقد بيانات مقبول 24 ساعة، وزمن استعادة حتى 60 دقيقة. لا يُعدان سياسة معتمدة قبل أن يوافق مالك النظام على ملاءمتهما للعمل.

## 8. اختبار الأداء والأعطال

تُثبت مواصفات الجهاز، ونسخة التطبيق، وحجم البيانات ومزيج الطلبات قبل القياس. الأرقام التالية **أحمال وأهداف أولية مقترحة وليست نتائج محققة**؛ تُعدل قبل التشغيل إذا كشف حجم العمل الفعلي الحاجة إلى غيرها.

| الملف | البيانات والحمل | القياس |
| --- | --- | --- |
| قبول أولي | 1,000 صنف، 500 طرف، 10,000 فاتورة وقرابة 30,000 سطر، 5 مستخدمين متزامنين | إحماء 5 دقائق، ثم قياس 15 دقيقة؛ p50 وp95 وأخطاء الخادم والذاكرة وانتظار الأقفال |
| نمو | 100,000 فاتورة وقرابة 300,000 سطر، مع حركة مرتجعات ونقد وتصنيع ممثلة | تصعيد المستخدمين 5 ثم 10 ثم 20؛ تحديد حد التشغيل العملي ونقاط البطء |
| تعافٍ | فقد استجابة عميل، فشل محقون قبل الالتزام، وإيقاف خادم اختبار أثناء عملية | مقارنة الحالة قبل وبعد التعافي وإعادة المحاولة؛ لا مستند جزئي أو خصم مكرر |

أهداف ملف القبول الأولي المقترحة: p95 أقل من ثانيتين للقراءات الشائعة، وأقل من 3 ثوانٍ للحفظ، وأقل من 5 ثوانٍ للوحة التقارير؛ صفر أخطاء خادم غير متوقعة وصفر فقد أو تكرار مالي. استجابات الرفض المتوقعة للصلاحيات والبيانات المعيبة تسجل منفصلة عن أخطاء الخادم. حمل النمو قياس سعة؛ لا يُشترط تحقيق أهداف الحمل الأولي عند 20 مستخدمًا إلا إذا كان هذا هو حجم التشغيل المطلوب.

لا يكفي متوسط الزمن لإعلان النجاح. تُراجع استعلامات تحميل كامل السجل، والأقفال، والعمليات التي تتجاوز مهلة المعاملة، وتُثبت أن إجماليات التقارير لم تتغير نتيجة تحسين الأداء أو تقسيم القوائم.

## 9. الأدلة وإدارة العيوب

يُنشأ عند التنفيذ مجلد `reports/acceptance-<run>/` يحوي وصف البيئة وبصمة المرشح، وسجل الحالات، والمطابقات الرقمية، ونتائج الصلاحيات، وسجلات الاستعادة والترقية والأداء، ولقطات المتصفح، والتقرير النهائي. تحفظ النسخ والسجلات التي تتضمن بيانات خاصة في مكان خاص خارج Git؛ تنقح الأسرار وملفات الجلسات من الأدلة المنشورة.

السجل القابل للتعبئة: [acceptance-results-template.csv](./acceptance-results-template.csv). الحالات المسموحة: مخطط، جارٍ، ناجح، فاشل، محجوب، غير منطبق مع سبب. يتضمن كل فشل خطوات إعادة إنتاج، والنتيجة المتوقعة والفعلية، وشدته، وملف الدليل، ونسخة الإصلاح ونتيجة إعادة الاختبار. أي تغيير في المتوقع يحتاج تفسيرًا ومراجعة المصدر المستقل.

الأولوية P0: فقد/تلف بيانات أو وصول غير مصرح واسع؛ توقف فوري. P1: حساب مالي خاطئ أو تجاوز صلاحية أو فشل دورة/استعادة أساسية؛ يمنع القبول. P2: خلل محدود أو بصري له حل مؤقت؛ يوثق أثره وتُحسم ملاءمة تأجيله قبل القبول.

الأوامر القائمة لتنفيذ خط الأساس، داخل نسخة العمل المخصصة للاختبارات:

```sh
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run build
```

تجري إعادة الاختبار بعد إصلاح عيب على حالته والحالات المرتبطة به. قبل إصدار حكم القبول، تنفّذ المجموعة المطلوبة على المرشح النهائي. لا يُعاد نفس الفحص لمجرد زيادة عدد مرات النجاح إذا لم تتغير النسخة أو البيئة ولم تظهر مشكلة جديدة.

## 10. بوابة القبول ومخرجاتها

- نجاح حالات P0 وP1 وكل دورة تشغيل حرجة؛ لا حالات حرجة محجوبة أو غير منفذة.
- تطابق السيناريو المستقل والسيناريوهات الذهبية، ومطابقة أرصدة العمل مع مصادرها وإغلاق فرق الافتتاح غير المبرر قبل الاعتماد المالي.
- منع القراءة والكتابة والإلغاء خارج الصلاحية، ومنع كشف الحقول المحمية وإعادة استخدام الجلسات المبطلة.
- سلامة المعاملات والتزامن: لا كميات سالبة غير مسموحة ولا حفظ جزئي ولا مستندات مكررة بسبب إعادة المحاولة.
- استعادة مثبتة، وترقية مثبتة، ونسخة نشر مرتبطة بالكود المختبر، وقياسات أداء ضمن نطاق التشغيل المتفق عليه.
- اعتماد مالك النظام لدورة العمل ومراجعة مالك البيانات/المحاسب للمطابقة؛ توثيق أي عيوب P2 مؤجلة بوضوح.

التقرير النهائي يقرر بشكل منفصل: **سلامة المرشح البرمجي، اعتماد البيانات المالية، وجاهزية التشغيل والنسخ**. نجاح أحدها لا يُستخدم لإعلان نجاح البقية. النتيجة تكون «جاهز ضمن النطاق المختبر»، أو «جاهز تقنيًا وتبقى متطلبات محددة للبيانات/التشغيل»، أو «غير جاهز بسبب عيوب مؤثرة»، مع الأدلة والخطوة التالية لكل بند.
